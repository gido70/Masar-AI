# Masar AI V5.5 — Trainer Portal

## Access model

- Owner: reads and manages steps, evidence, versions, profiles and feedback.
- Trainer: reads approved project records and creates feedback only.
- Pending: authenticated but cannot open project records until owner approval.
- Public visitor: uses the public Masar AI product and cannot access the trainer portal.

## Safe deployment order

1. Review `20260829_trainer_portal.sql`.
2. Review `20260830_masar_steps_1_12_alignment.sql` so database-backed cards also show 12/24.
3. Apply both migrations, in timestamp order, to the intended Masar AI Supabase project.
4. Sign in once as the owner.
5. Promote the owner's exact Auth UUID using the one-time SQL shown at the bottom of the first migration.
6. Add the project URL and publishable key to `assets/js/masar-supabase-config.js`.
7. Test pending, trainer and owner roles before publishing.
8. The trainer signs in once, remains pending, then the owner approves the exact account.

## Security rules

- Never use `service_role` in GitHub Pages or browser JavaScript.
- A new signup is always pending and unapproved.
- Trainer writes are limited to feedback authored by the same authenticated user.
- Only the owner updates project records, feedback status and owner responses.
- GitHub remains the source of truth for code and migrations; Supabase stores live portal data.

## Visibility rules

- The portal shows only approved progress, outputs, evidence, versions, tests and trainer feedback.
- The portal does not show owner presentation scripts, anticipated questions, competition strategy, internal weaknesses, credentials, storage administration or private capacity decisions.
- Steps 1–12 mirror the approved worksheet; steps 13–24 remain untitled until the trainer explains them.
- The current landing-page promise avoids unverified time claims and distinguishes tested results from reviewed information.
